## 3. Serialized vocabulary and migration rules

### 3.1 What the new vocabulary requirement means

The task is not to invent replacements for three edge names. It is to stop requiring those names in credentials. Keep institutional distinctions in the evaluator while reading credential-native evidence under accepted bindings.

| Old surface                                          | New treatment                                                                                                                                                                                                             |
| ---------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `evidence[].relation = authorizedBy`                 | Interpret a recognized authorization policy/reference in `termsOfUse`, or an explicitly supported independently authoritative grant mechanism.                                                                            |
| `evidence[].relation = derivedFrom`                  | Establish operational-scope maintenance permission plus containment through the selected authorization binding. Genuine provenance may additionally be represented using PROV-O; it does not discharge either obligation. |
| `evidence[].relation = supportedBy`                  | A recognized supporting evidence entry in `evidence`, with profile-defined applicability to requested claims.                                                                                                             |
| Serialized `authorizationBasis.kind`                 | Extract the appropriate grant/activity/basis from authoritative native facts and profile rules. Do not copy the old field into a newly named generic wrapper.                                                             |
| Custom edge digest                                   | Use the selected standard resource-integrity mechanism with its exact representation rules. Independently verify the referenced credential when it is required.                                                           |
| Mandatory custom per-claim parent pointer            | Remove from the core credential contract. Emit a verifier-owned claim-to-record/path witness. Preserve native claim links where the actual domain standard defines them.                                                  |
| `PASS`, `FAIL`, `WARN`, `SKIP` in credential schemas | Remove as credential vocabulary. Internal execution/report labels may remain with explicit semantics and no influence through error counting.                                                                             |
| Old graph JSON supplied as authoritative input       | Treat only as legacy input or UI metadata. Compile the operative graph from authenticated native facts and accepted profile rules.                                                                                        |

Unknown optional annotations need not make a VCDM document invalid. An unrecognized term, policy type or relation required for the reliance request must not establish an obligation. Distinguish base-format validity from supported-profile sufficiency.

### 3.2 Standard carrier responsibilities

Use the VCDM2 mechanisms in their defined roles: `termsOfUse` for recognized policy/authorization interpretation, `evidence` for supporting information, `relatedResource` for resource integrity, and `credentialSchema` for applicable validation. DCMI conformance declarations identify profiles but do not require the verifier to trust them. These reuse choices follow the agreed VC4QI design; VCDM2 alone does not supply the QI decision rules. See [VCDM2, 15 May 2025](https://www.w3.org/TR/2025/REC-vc-data-model-2.0-20250515/), particularly §§4.11, 5.3, 5.5–5.6 and 7.

Do not promote `TrustFrameworkPolicy`, `IssuanceCertificate`, `scopeRef`, `grant`, or any example-context term to a universal VC4QI field by naming it in code. First establish the exact binding that defines it. An EBSI v1 payload cannot simply receive a VCDM2 context and become EBSI v2 conformant.

If no deployed authorization binding supports the complete RM example, implement a **documented local experimental binding** for the fixture, with a versioned context, schema and interpretation. Reuse suitable existing terms; explicitly list the few domain terms that remain local. Place local terms in an unmistakably experimental namespace (for example a reserved `.example` namespace resolved by the fixture loader), never an asserted external institution's namespace. Such a binding is an executable research fixture, not an externally governed production profile. This is authorized here to avoid either fabricating a standard or leaving the demo inoperable. No new universal graph vocabulary is authorized.

### 3.3 Mandatory binding manifest

For each supported binding, publish a machine-readable manifest and a concise human-readable table containing:

1. Stable binding/profile identifier, version, experimental/production status and owning governance source.
2. Accepted carrier/model versions, credential types and exact contexts/schemas/shapes.
3. Exact expanded IRIs and native paths used for grantor, grantee, activity, scope, supporting references and applicable times.
4. Cardinality rules: object versus collection, multiple subjects, multiple policies, multiple schemas and multiple status entries where supported.
5. How references are found and secured; how independently discovered grants are authenticated and bound to the actor.
6. Recognized policy/evidence types and what each can establish.
7. Rules for principal equality, identity mappings, grant permission and operational-scope maintenance permission.
8. Scope dimensions, units, boundary inclusivity, missing/empty semantics, mapping versions and supported evaluator identifiers.
9. Complete route requirements and global restrictions.
10. Proof, key discovery, status, temporal/freshness and resolver rules.
11. Required support, disclosure, presentation and object-applicability conditions.
12. Test-vector locations and unsupported cases.

The manifest is implementation configuration, not a new credential vocabulary. Exact spellings are an implementation choice; semantic content above is mandatory. Never allow it to load arbitrary executable code from an issuer-supplied URL.

### 3.4 JSON-LD, native data and signatures

* Pin dependency content and loader mappings; do not silently resolve a different schema/context version.
* Expand all decision-relevant JSON-LD terms correctly; reject protected-term redefinition and decision-relevant data lost through unsafe expansion.
* Do not repair a credential's context or rename fields before checking the protection over its original representation.
* Regenerate migrated synthetic credentials with fresh deterministic test signatures. Do not edit a signed JSON document and retain its old proof.
* Keep external XML in its native representation. A wrapper digest establishes content binding under the selected mechanism; it does not manufacture an XML signature or transfer an original signature onto re-encoded JSON.
* Multiple representations must be checked for decision-relevant agreement where the profile relies on them together.
* Do not invent a generic canonical JSON digest. Byte digests, suite transforms and RDF canonicalization are distinct and must follow their selected specifications.

### 3.5 Legacy compatibility

The default new path must not emit or depend on the legacy edge serialization. Prefer a separate explicit legacy adapter over a permissive auto-detect fallback.

A legacy adapter verifies the original secured legacy representation and preserves provenance, then produces internal facts under an explicitly selected legacy profile. It must not claim that a converted credential retains the original signature or meets the new profile. New-profile requests reject or mark unsupported a legacy-only authorization representation. Legacy fixtures may remain in a clearly separated test directory.

Document the public API/schema compatibility break. Choose a coherent new version using repository release conventions; do not silently call changed wire semantics the same profile version.

## 4. Evaluator request and result

### 4.1 Request

The request explicitly supplies: target credential identity; selected claims; purpose; accepted profile and version; trust configuration; relevant evaluation/activity times; supplied evidence; resolver policy and budgets; and, when requested, conformity requirement and decision rule.

Select a processing plan through verifier policy, not by taking the first type/context/schema in a credential. Multiple declarations require a deterministic accepted composition. A credential cannot choose a weaker profile than the verifier accepts.

An empty target claim selection must have an explicit supported meaning. Do not accept an empty claim list accidentally through vacuous conjunction.

### 4.2 Three evidence states, plus execution state

Use the internal semantic states `established`, `contradicted`, `not_established`. Separately record `not_run` when a check was not executed. These names belong to internal/report schemas, not VCDM credential vocabulary.

* **Established:** adequate validated evidence supports the predicate under the selected profile.
* **Contradicted:** a supported check establishes a mismatch or violation.
* **Not established:** missing, unresolved, unsupported, budget-limited or otherwise insufficient evidence prevents a definite conclusion.
* **Not run:** execution metadata only; cannot satisfy an obligation.

For conjunction, one contradiction is enough for contradiction; all conjuncts must be established for establishment; otherwise the result is not established. For disjunction, one established complete alternative is enough for establishment; all alternatives must be contradicted for contradiction; otherwise the result is not established. Search that stops at a resource limit cannot claim to have disproved all alternatives.

Do not use `failures.length === 0`, absence of exceptions, or absence of top-level FAIL as acceptance logic. Unknowns and omissions must participate in the obligation evaluation itself.

### 4.3 Result contract

Return separate results for document protection/verification, authorization, support, and conformity, together with the overall reliance outcome `accept`, `reject`, or `not_established`. Define the scope of every boolean if retained for compatibility. A document-level `verified: true` must not imply reliance.

The exact JSON shape is a software API choice. A suitable result contains:

```text
requestId, target, selectedClaims, purpose, profile/version
verification: per-artifact applicable structure/protection/temporal outcomes
authorization: per-claim state, complete route witnesses, restrictions
support: per-obligation state and applicability witnesses
conformity: per-claim state or explicit not-requested/not-run, rule and arithmetic
reliance: accept | reject | not_established
trace: gate, node-use, predicate, state, reason, input provenance
resources: content identities, retrieval sources/times, status observations
limitations: exact skipped, unsupported or simulated mechanisms
```

For a required conjunction of claims, all must satisfy the request. If the product supports partial results, disclose exactly which claims are covered; do not turn one authorized claim into acceptance of the complete credential.

Internal diagnostics may keep stable uppercase codes. Map HTTP operation errors to documented RFC 9457 Problem Details when an HTTP surface exists. `authorization-not-established` is an application problem type, not a new VC property. Semantic rejection need not be an HTTP protocol failure; document the API choice.

## 5. Graph compilation, identity and ordering

### 5.1 Small internal model

Represent an artifact separately from a use of that artifact. A node-use is distinguished by content identity, role, purpose, profile/processing plan and relevant time context. Identical document bytes may discharge different obligations for different purposes.

The internal graph may contain typed obligations and edges for visualization. Internal names such as authority use, bounded projection, recognition or support are permitted. Removing the serialized vocabulary does not mean deleting the distinctions or the graph inspector.

Every operative relation needs an evidence source: a protected source pointer or an independently authenticated authoritative grant/discovery fact, its binding adapter, and the rule that gives it meaning. A holder-provided graph or arbitrary extra VC cannot create an endorsement.

### 5.2 Required algorithmic sequence

1. Select the accepted plan and parse bounded input. Do not execute arbitrary user-supplied evaluation modules.
2. Identify candidate references and check resource identity constraints. Candidate discovery is not acceptance.
3. Verify original secured artifacts, authorized key relationships and applicable temporal evidence.
4. Map protected native facts through accepted deterministic mappings, retaining source paths and transformations.
5. Compile permitted relation obligations, required support and complete route candidates.
6. Recursively discharge every required node-use; memoize by the complete evaluation context.
7. Establish complete authorization routes and global restrictions per claim.
8. Establish required supporting evidence and its applicability to the requested object/activity.
9. Evaluate conformity only when requested and its prerequisites are established.
10. Produce deterministic witnesses and an auditable result. Trace order may differ internally, but its meaning must be stable across languages.

### 5.3 Seven gates: canonical numbering for this migration

Older documents number gates differently. Use this table consistently in code, tests, docs and UI.

| Gate | Obligation             | Required evidence                                                                                                |
| ---- | ---------------------- | ---------------------------------------------------------------------------------------------------------------- |
| 0    | Plan and structure     | Accepted purpose/profile; deterministic dispatch; supported native structural constraints                        |
| 1    | Resource identity      | Exact referenced representation/version where required; no silent conflicting identities                         |
| 2    | Protection             | Correct proof/security verification and authorized key/controller relationship; authenticated security artifacts |
| 3    | Temporal applicability | Relevant validity intervals, status/freshness and historical requirements                                        |
| 4    | Meaning and mapping    | Supported identifiers, quantities, units and decision-preserving native interpretation                           |
| 5    | Authority and scope    | Principal binding, rights, complete routes, operational containment, global restrictions                         |
| 6    | Support and decision   | Independently justified applicable support; requested conformity calculation                                     |

This is a per-node-use dependency discipline, not a ban on all parsing or equality checks before gate 2. Suite transformations and structural checks necessarily occur before/during cryptography. Authenticated key resolution can be required at gate 2, while institutional authority remains a separate gate-5 obligation. Security/status resources have their own applicable checks. No failed lower-stage business fact may establish a higher-stage predicate.

Diagnostic evaluation of a failed object must remain inert: it cannot confer authority, poison accepted caches or trigger uncontrolled network access. Failures in unused route alternatives are retained as diagnostics, not automatically global rejections.

### 5.4 Identity, cache and cycle rules

* Bind immutable artifact identity to the selected secured representation and processing context, not only to a fetch URL.
* Detect conflicting content claiming the same immutable identity within one evaluation; do not last-write-wins merge it.
* Preserve distinct time-stamped observations for dynamic status resources. Do not freeze status indefinitely merely because the resource URL is pinned.
* Cache verified artifacts separately from reliance outcomes. Outcome caches include purpose, profile, role, relevant times, trust-configuration identity and dynamic-evidence freshness.
* Detect cycles on the active recursive evaluation stack. Shared DAG dependencies must not be mistaken for cycles because they appear in a global visited set.
* All required recursive relations, including support and external attestations' authority dependencies, need a well-founded justification. A required circular obligation gives not established in the baseline model.
* A cycle in unrelated provenance data does not invalidate a complete independent route.
* A configured anchor supplies only its configured authority for relevant purposes. A self-signature, a familiar institutional name or a maximum traversal depth is not an anchor.

## 6. Authority and scope semantics

### 6.1 Principal and granting-right checks

For an authorizing relation, bind the grantee in the authoritative parent to the actor exercising the right in the child. A missing actor/subject never silently bypasses the comparison. The same check is required for a bounded operational projection, together with permission to maintain/project the scope. Multiple subjects require selecting the actual applicable grant, not the first subject.

Key authorization and institutional permission are separate. A correct signature from an entity does not show that it may accredit, recognize, delegate, maintain an operational scope or issue a particular domain result.

Treat identity equivalence as governed input. Do not equate legal entity names, lowercased strings, URL aliases, organization brands or DID controllers to institutional authority without a supported binding.

An authority-use relation asks whether a result's issuer may perform that activity under an operative grant. A bounded projection asks whether the projected authority remains within its parent and the projecting actor has that permission. Do not apply subset checks to every independent institutional grant; do not omit them from operational projections.

### 6.2 Complete routes and global restrictions

The profile defines permitted complete routes. For a claim:

```text
authorized(claim) = applicable_global_restrictions_hold
                    AND OR_over_complete_routes(
                          AND_over_required_bases(basis_established))
```

For example, a fictional profile may allow `(competence AND scheme permission) OR statutory authority`. This is a profile example, not a universal GS or legal rule.

Rules:

* Every required basis in a route must be tied to the correct actor, activity, time and claim.
* One record must cover all dimensions owned by that basis. Do not splice property from one record with method from another.
* Complementary bases can govern different dimensions legitimately. Check all overlapping restrictions; the profile defines ownership and combination.
* Alternative complete routes are OR; parts of different routes do not combine into a synthetic route.
* Global restrictions apply outside the OR. A suspension governing the whole activity cannot be bypassed by selecting another route.
* Not every failed/revoked unrelated credential is a global restriction. The accepted policy must establish its applicability.
* An empty route or missing requirements list cannot accidentally authorize arbitrary claims. Explicit anchor-only cases need an explicit profile rule.

### 6.3 Scope records, mappings and quantities

Implement scope evaluators per domain binding. The core invokes them without assuming all quantities are pressure or all categorical terms are comparable.

Required rules:

1. Use governed identifiers or explicitly accepted equivalence mappings. Human-readable labels are display-only. `As` must not match `Ash`; CuZn39Pb3 must not match CuZn40Pb2 by partial spelling.
2. One complete record covers each relied-upon claim. Different claims may use different complete records.
3. A delegated interval must fit one complete parent interval in the baseline profile. Adjacent records do not automatically authorize their union.
4. Define lower/upper inclusivity, empty/missing constraints and dimension orientation in the profile. Missing restricted dimensions are unresolved or invalid, never silently unrestricted. An explicitly permitted unrestricted dimension is different.
5. Validate quantity kind, unit identity, magnitude, finite values, interval ordering and uncertainty metadata before comparisons. Reject contradictory unit indicators. Unsupported conversions yield not established.
6. Preserve quantity-kind distinctions even when dimensions coincide. Do not infer semantic equivalence from unit dimensionality alone.
7. Test representation equivalence deliberately: `1 mg/kg = 10^-6 kg/kg` in the mass-fraction profile. Do not send RM mass fractions through `toPa`.
8. Use deterministic decimal/rational arithmetic or a documented numerically sound comparison strategy across TypeScript and Python. Do not silently insert a tolerance that changes the acceptance boundary.
9. Preserve asymmetric uncertainties, coverage factors and distributions where required. If the baseline supports only symmetric expanded uncertainty, identify unsupported inputs rather than averaging them.
10. Test empty result groups, uncertified properties and partially omitted claim fields. Filtering non-relied-upon data is allowed; filtering requested claims into an empty accepted set is not.

Quantity-binding policy: retain native DCC/D-SI XML where applicable; use a pinned SIS/SIRP mapping for the selected RDF profile where validated. QUDT may remain in an explicitly named legacy or alternative binding. Do not mix ecosystems by assuming equal-looking unit labels imply equivalence. Resolve and document exact available ontology terms; do not invent plausible SIS term names. The complete RM baseline can use a clearly scoped experimental quantity binding until an external mapping is validated, with that limitation stated.

### 6.4 Uncertainty and conformity

Keep three possible uses separate:

* A calibration capability floor, when the selected calibration profile requires it: reporting uncertainty below the admitted capability may contradict scope.
* A customer's maximum usable uncertainty, only if requested: a reliance requirement separate from accreditation.
* A conformity decision rule such as `x + U <= L`, explicitly chosen for the example.

Do not reintroduce the old generic RM uncertainty ceiling. Do not reuse the same inequality for all three purposes. A valid uncertainty representation remains necessary when a conformity calculation consumes it.

### 6.5 RM baseline that must run end to end

Use fictional, clearly labeled authorities. Keep all non-varied identity, time, method, support and protection conditions valid.

* A: accreditation of the RM producer; authorized mass-fraction range `[50, 500] mg/kg`; methods M1 and M2 allowed.
* O: controlled operational scope for that producer; same example range, M1 only. Its authorization binding establishes maintenance permission and containment within A.
* D: RM certificate for CuZn39Pb3 brass, arsenic mass fraction, method M1, symmetric expanded uncertainty `U = 5 mg/kg`, coverage factor `k = 2`.
* S: required supporting study for the same relevant material/batch and purpose; its laboratory authority H is established separately.
* Q/r: verifier limit `L = 200 mg/kg`; guarded acceptance `x + U <= L`. The accredited range compares the estimate x in this profile, not the guarded quantity.

| Target x  | Scope calculation  | Conformity calculation | Required result                                          |
| --------- | ------------------ | ---------------------- | -------------------------------------------------------- |
| 178 mg/kg | `50 <= 178 <= 500` | `178 + 5 = 183 <= 200` | accept if all other obligations established              |
| 197 mg/kg | `50 <= 197 <= 500` | `197 + 5 = 202 > 200`  | reject for conformity; authorization remains established |
| 520 mg/kg | `520 > 500`        | not run                | reject for scope; never label it a conformity rejection  |

Add two boundary controls: `195 + 5 = 200` satisfies the inclusive conformity rule; x=500 remains in the inclusive scope even though this particular conformity requirement rejects it. A separate authorization-only request for x=197 succeeds without running conformity. An x below 50 fails scope. A method M2 claim cannot use O merely because A admits M2; it needs a separately permitted complete route.

### 6.6 Governed method succession and semantic boundary

Implement explicit profile inputs that distinguish a scheme permitting M2 as an accepted successor of M1 from a scheme requiring an explicit extension. Identical credential bytes can then produce different justified scope outcomes under two explicitly selected profiles. Without an accepted succession interpretation, return not established. A self-asserted equivalence by the result issuer cannot override governance.

Document the boundary as underdetermination without accepted interpretation, not a proof that every scope question is mathematically undecidable. Conditional decidability additionally assumes supported terminating evaluators, finite route search and a well-founded required dependency graph. Resource timeout is not a proof of semantic falsity.

## 7. Protection, resources, trust and time

### 7.1 Protection and trust anchors

* Every required credential receives the real protection checks required by its selected binding. At least one baseline end-to-end suite runs without `skipProof`, placeholder proofs or an always-successful verifier.
* Verify signatures using the appropriate key relationship/controller and suite. A signature from any key returned by a resolver is insufficient.
* The resolver must map the requested verification method to the correct fixture identity. A constant resolver returning the same key for all requests is not adequate adversarial evidence.
* Authenticate registry/trust-list artifacts before using their contents. Anchor selection is independently configured and must not become circular through the registry being evaluated.
* Authenticate a status artifact and establish that its signer is permitted to state status for the target under the selected mechanism. URL possession or a valid unrelated signature is insufficient.
* A proof-disabled exercise may remain available as a clearly named simulation. It must never yield an unconditional successful reliance result or be counted as a cryptographic end-to-end pass.

### 7.2 Resource handling

Put all network I/O behind a bounded resolver: permitted protocols/origins, redirect checks, address restrictions, media-type expectations, response-size/decompression limits and timeouts. Validate redirects and resolved destinations; an initial allowlisted URL alone is insufficient. Fixture loaders use an explicit local resource catalog and do not silently phone home.

Verify supplied integrity metadata according to the chosen binding before using the resource. A correct digest identifies content; it does not establish that its author is entitled to grant authority. Distinguish digest mismatch from resource unavailable.

Tests must not depend on live W3C URLs for static contexts. Vendor the pinned normative/test context resources with origin/version/hash metadata and resolve their canonical identifiers locally. Live integration tests are a separately marked lane. This fixes reproducibility without disabling safe processing or cryptographic checks.

### 7.3 Time model

Separate evaluation time, activity/measurement time, native issuance time if defined, validity interval, proof timestamps, status observation time and material shelf life. Do not treat `validFrom` as issuance time merely because a fixture historically did so. An accepted profile may define a particular relationship explicitly.

The baseline supports a precise current-reliance question. Historical requests require the evidence that the selected temporal policy needs. When authenticated historical status/scope is unavailable, report not established rather than substituting current status. A current suspension can affect new reliance according to the policy without proving past issuance was unauthorized.

Missing status is governed by the accepted profile. VCDM optionality does not imply that a profile requiring revocation evidence should pass without it. Freshness is explicit; holder-supplied signed status is neither automatically acceptable nor automatically stale. Its admissibility depends on authenticated observation time, purpose and the profile's freshness rules.

Trusted time mechanisms may be provided behind a port. Do not implement new timestamp-service infrastructure in this migration or claim backdating resistance from issuer-written dates alone.

## 8. Required support and external scope attestations

### 8.1 Supporting evidence is independently evaluated

A required study/report/calibration must be valid for its own role and supported by the relevant authority, then matched to the requested material, batch, instrument, activity, method and time as the profile requires. It need not have the same subject as the issuer of the consuming result. That equality is an authority-binding rule, not a universal support rule.

A genuine report concerning another batch contradicts support applicability. A missing report leaves support not established. A resolved URL, correct digest or verified signature alone does not establish support sufficiency. Plain provenance cannot satisfy a required authorization obligation.

Physical-object assurance is explicit: equality of protected identifiers establishes the digital match the profile defines, not that nobody swapped the physical sample. Do not claim anti-counterfeiting or physical truth from this evaluator.

### 8.2 External authority-issued answers

Support an experimental adapter for an authority-issued scope answer as an alternative way to establish a **specific** scope predicate. This is additional evidence supplying governed semantics, not an escape from the semantic boundary.

The accepted profile specifies:

* Who is authorized to answer, and how that authority is established independently of the answer itself.
* The exact predicate: point-claim coverage versus full delegated-scope containment.
* The claim or claim digest, relevant grantee/activity, scope identity/version, rule/profile version, applicable time and question parameters.
* Required answer protection, validity/status/freshness and whether historical reliance is supported.
* Whether a supplied answer can satisfy the request without a network query.

Before using an answer, verify its protection, bind the signer to the permitted authority, bind its content to the exact question, check applicable time/version and any required status, and evaluate the stated result. A correct answer for another claim, another grantee, a later scope version or a different activity time cannot be reused. An endpoint URL selected only by the applicant cannot determine its own authority.

A signed answer that says 'this point is covered' cannot establish that a broader O is contained in A. External-attestation reliance shifts an assumption to the recognized attesting authority; report that basis in the witness. If the authority is unavailable and no admissible answer was supplied, return not established. Do not recursively trust the answer to authorize its own signer.

## 9. Recognized Entities and other infrastructure bindings

### 9.1 W3C Recognized Entities: scoped experimental adapter

The [6 September 2026 Working Draft](https://www.w3.org/TR/2026/WD-vc-recognized-entities-1.0-20260906/) defines `RecognizedEntityCredential`, `recognizedIn`, `recognizedTo` and `RecognizedAction`, including schema-based `outputValidation`. It is experimental. Use this exact snapshot for an initial adapter; a later version requires explicit review, manifest update and tests. Recognition and action recognition do not by themselves supply every VC4QI reliance obligation.

Implement this in an optional binding module, not by requiring every credential to become a RecognizedEntityCredential or using its terms as universal graph edges. Minimum scope: credential-based discovery, protected membership/principal matching, configured anchors, action matching, accepted output validators and conversion to the internal authority evidence interface. Test a small signed recognition chain and a result whose recognition succeeds but QI scope does not.

If identifier-based discovery is implemented, §4.2 requires verification of the retrieved presentation and its binding to the queried issuer; checking only enclosed credentials is not enough. Otherwise declare this discovery path unsupported and return an explicit unsupported result when requested. Do not advertise full draft conformance from the minimum adapter.

Where a profile wants both baseline `termsOfUse` interpretation and Recognized Entities discovery, define their composition. Do not automatically merge their grants or require duplicate references in every leaf. Reaching a recognition anchor does not override global restrictions, substitute for a supporting study or decide conformity.

### 9.2 EBSI, EUDI/EUBW and carrier neutrality

Keep carrier/security, authority source and domain semantics independently selectable through supported profiles. Do not build all wallet stacks to complete this task.

* EBSI integration is optional and requires exact environment, data-model version, schemas, credential types, APIs and conformance evidence. Avoid mixing v1 `IssuanceCertificate` examples with unrelated v2 terms.
* SD-JWT VC, mdoc and W3C VC are not interchangeable JSON envelopes. A claim named `evidence` may have different governed semantics. A payload extension is not automatically an authorization reference.
* Distinguish wallet support obligations, legally recognized formats and realizations in a technical profile. Do not assert current legal status from old notes or infer production support from a draft.
* Recheck the exact ETSI clauses before changing European documentation. Earlier supplied notes contain conflicting statements about which realizations permit evidence; this handover does not resolve those conflicts by assumption.
* `extends` or similar credential-type inheritance never automatically means institutional delegation or scope containment.
* Preserve presentation-query integration where useful, but DCQL/Presentation Exchange request matching does not execute the reliance calculus.

Mark unsupported adapters honestly. A port stub is not an implemented integration. Remote normative/legal verification is required if making corresponding current compliance claims; it is not a reason to block the coherent local RM implementation.

## 10. Presentations and selective disclosure
